# 系统报障与需求管理子模块 — 系统方案

## 一、目标与范围

业务人员提出优化建议或报告 BUG 时，在本系统提交工单并上传附件；IT 人员在监控台集中查看、指派处理人；处理人填写处理记录并提交结果；提交人验收后关闭。全程留痕，站内消息推动流转。

**不新建用户体系**：所有人员复用现有登录账号（`usercode`），不碰 ERP 账户表。

## 二、角色与权限（按 ERP 岗位自动识别）

角色由两部分决定，既满足"按 ERP 岗位自动识别"，又不需要在代码里写死岗位编码：

1. **人员来源**：`ucsdb.ent_account_dept_post` 关联 `ucsdb.ent_post`，取该用户的主岗位（`ismain=1`）
2. **角色映射**：`bidb.ops_issue_role_cfg` 配置哪些岗位编码属于 IT 管理员 / 处理人，页面可维护

登录时按 `usercode` 解析出角色：

| 角色 | 判定 | 权限 |
|---|---|---|
| IT 管理员 | 主岗位在 `role_cfg` 中配置为 `IT_ADMIN` | 监控全部工单、指派、调优先级、强制关闭、维护角色配置 |
| 处理人 | 主岗位配置为 `HANDLER` | 查看指派给自己的工单、填处理记录、提交结果 |
| 提交人 | 所有登录用户 | 新建、查看自己提交的、补充备注、验收、撤回 |

一个人若岗位同时匹配多个角色，取并集（既可监控也可处理）。

## 三、数据模型（5 张表，全部建在 bidb）

### 3.1 `bidb.ops_issue` 工单主表

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT AI | 主键 |
| `issue_no` | VARCHAR(32) | 工单号 `BK-20261127-0001`，唯一 |
| `issue_type` | TINYINT | 1=需求 2=BUG |
| `title` | VARCHAR(200) | 标题 |
| `description` | TEXT | 详细描述（BUG 用） |
| `requirement_json` | TEXT | 需求结构化字段 JSON（仅需求类型，见 3.1.1） |
| `module` | VARCHAR(100) | 涉及模块 Affected modules |
| `priority` | TINYINT | 1=紧急 2=高 3=中 4=低 |
| `status` | TINYINT | 见状态机 |
| `reporter` / `reporter_name` | VARCHAR(50)/(200) | 提交人账号/姓名（冗余姓名防岗位变更） |
| `assignee` / `assignee_name` | VARCHAR(50)/(200) | 处理人账号/姓名 |
| `assigned_by` / `assigned_time` | VARCHAR(50)/DATETIME | 指派人/时间 |
| `created_time` / `updated_time` / `closed_time` | DATETIME | 创建/更新/关闭时间 |
| `close_remark` | VARCHAR(500) | 关闭备注 |

索引：`issue_no` 唯一、`status`、`reporter`、`assignee`、`created_time`

### 3.1.1 需求结构化字段（标准需求申请单模板）

仅 `issue_type=1`（需求）使用，统一存于 `ops_issue.requirement_json`，字段：

| JSON 键 | 中文/英文字段 | 必填 |
|---|---|---|
| `background` | 业务背景与现状 / Business Background & Current Situation | 是 |
| `pain_points` | 业务问题与痛点 / Business Problem & Pain Points | 是 |
| `scenario_5w1h` | 需求场景 (5W1H) / Business Scenario (5W1H) | 是 |
| `detailed_description` | 详细需求描述 / Detailed Requirement Description | 是 |
| `roles` | 业务场景角色 / Business Roles Involved | 是 |
| `proposed_solution` | 建议解决方案 / Proposed Solution | 否 |

“涉及模块”沿用 `module` 列，“需求名称”沿用 `title` 列，“关联附件”沿用附件表，“优先级”沿用 `priority` 列。BUG 类型仍使用原来的标题/模块/优先级/描述简单表单。

已建库的表执行增量脚本：`deploy/sql/bidb_issue_requirement_fields.sql`（幂等，可重复执行）；全新安装直接执行 `deploy/sql/bidb_issue.sql` 即可。

### 3.2 `bidb.ops_issue_log` 流转记录

`id`、`issue_id`、`action`(create/assign/start/process/verify/reject/reopen/cancel)、`action_name`、`operator`、`operator_name`、`content`(TEXT)、`created_time`。索引 `issue_id + created_time`。

### 3.3 `bidb.ops_issue_attachment` 附件

`id`、`issue_id`、`file_name`、`file_path`(相对路径)、`file_size`、`file_type`、`uploader`、`created_time`。索引 `issue_id`。

### 3.4 `bidb.ops_issue_role_cfg` 岗位角色配置

`id`、`postcode`、`postname`、`role`(IT_ADMIN/HANDLER)、`status`、`created_time`。唯一键 `(postcode, role)`。

### 3.5 `bidb.ops_issue_message` 站内消息

`id`、`receiver`、`issue_id`、`type`(ASSIGNED/PROCESSED/VERIFIED/REJECTED/REOPENED)、`title`、`content`、`is_read`、`created_time`。索引 `receiver + is_read`。

## 四、状态机

```text
待处理(1) --IT指派--> 已指派(2) --处理人接手--> 处理中(3)
处理中(3) --提交结果--> 待验证(4) --提交人验收通过--> 已关闭(5)
待验证(4) --验收不通过--> 处理中(3)（写明退回原因，记 log + 发消息）
待处理/已指派 --提交人撤回--> 已取消(6)
```

每次状态变更写一条 `ops_issue_log`，并给相关人员发站内消息。

## 五、页面设计（新增菜单分组「系统报障」）

| 页面 | 路由 | 可见性 | 内容 |
|---|---|---|---|
| 我的报障 | `/issue/my` | 所有人 | 新建按钮；自己提交的工单列表；状态/类型/关键字筛选 |
| IT 监控台 | `/issue/monitor` | IT 管理员 | 全部工单；顶部状态统计卡片；行内"指派"按钮 |
| 我处理的 | `/issue/assigned` | 处理人 | 指派给自己的工单；处理入口 |
| 角色配置 | `/issue/roles` | IT 管理员 | 从 ERP 岗位列表勾选 IT 管理员 / 处理人 |

**工单详情弹窗**：基本信息 + 附件列表 + 流转时间线 + 处理记录输入框；底部按钮按当前角色和状态动态显示（指派/接手/提交结果/验收/退回/撤回）。

**站内消息**：Header 加铃铛图标显示未读数，点击下拉列出消息，可标记已读/全部已读；点击消息跳转到对应工单详情。

**新建工单弹窗**：
- **需求**：按标准需求申请单模板填写，字段依次为涉及模块、需求业务说明（需求名称、业务背景与现状、业务问题与痛点、需求场景 5W1H、详细需求描述、业务场景角色、建议解决方案）、优先级、关联附件。除建议解决方案外均为必填。
- **BUG**：保持原来的标题、所属模块、优先级、描述、附件。

**附件必须与表单一次性提交**，不允许创建工单后再补传：提交时以 multipart/form-data 同时发送文本字段和所有附件，后端先校验全部附件（类型/大小），再创建工单并落库附件；任一步失败则补偿清理已写文件、附件记录、日志、消息和工单，保证不留残缺工单。详情页的附件区仍可在工单创建后继续追加上传。

需求提交时前端把 6 个结构化字段序列化为 `requirement_json` 一并提交，后端校验必填项后入库；详情页按模板字段逐项展示。

## 六、接口清单（约 20 个）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/issue/list` | `scope=my/monitor/assigned` + 筛选 + 分页 |
| POST | `/api/issue/create` | 新建工单（兼容旧调用，纯文本） |
| POST | `/api/issue/create-with-files` | 新建工单并同时上传附件（multipart，前端实际使用）；需求类型额外传 `requirement_json` |
| GET | `/api/issue/{id}` | 详情（含附件、流转记录） |
| POST | `/api/issue/{id}/assign` | 指派处理人 |
| POST | `/api/issue/{id}/start` | 接手处理 |
| POST | `/api/issue/{id}/process` | 提交处理结果 |
| POST | `/api/issue/{id}/verify` | 验收（通过/不通过） |
| POST | `/api/issue/{id}/reopen` | 退回重处理 |
| POST | `/api/issue/{id}/cancel` | 撤回 |
| GET | `/api/issue/{id}/logs` | 流转记录 |
| POST | `/api/issue/upload` | 附件上传（multipart） |
| GET | `/api/issue/attachment/{id}/download` | 附件下载（鉴权） |
| GET/POST/DELETE | `/api/issue/roles...` | 角色配置 |
| GET | `/api/issue/handlers` | 可选处理人下拉（按角色配置过滤） |
| GET | `/api/issue/messages` | 站内消息列表 |
| POST | `/api/issue/messages/{id}/read` | 标记已读 |
| POST | `/api/issue/messages/read-all` | 全部已读 |

GET 沿用现有 `?q=<JSON>` 传参约定；所有接口走 JWT 鉴权。

## 七、附件存储

- 物理路径：`backend/uploads/issue/YYYYMMDD/{uuid}.{ext}`
- 数据库只存相对路径 `uploads/issue/...`
- 白名单扩展名：png/jpg/jpeg/gif/pdf/doc/docx/xls/xlsx/txt/zip，单文件上限 10MB
- 下载走鉴权接口，不直接暴露静态路径
- Docker 部署时把 `uploads` 目录挂到宿主机，避免容器重建丢文件

## 八、通知规则

| 动作 | 接收人 | 类型 |
|---|---|---|
| IT 指派处理人 | 处理人 | ASSIGNED |
| 处理人提交结果 | 提交人 | PROCESSED |
| 验收通过 | 处理人 + 指派人 | VERIFIED |
| 验收不通过 | 处理人 | REJECTED |
| 提交人撤回 | 处理人（若已指派） | REOPENED |

## 九、非功能性

- 中英文 i18n 全覆盖，与现有页面一致
- 操作审计：所有写操作记 log，含操作人、时间、IP
- 权限校验在后端强制，前端只做展示控制
- 沿用现有 Element Plus 表格/弹窗风格和 `bidb` 建表方式

## 十、开发顺序与交付物

1. `deploy/sql/bidb_issue.sql` — 5 张表建表脚本（由你手工执行）
2. 后端 `services/issue_service.py` + `routers/issue.py` + 角色依赖注入
3. 前端 4 个 Vue 页面 + 消息组件 + 路由/菜单 + i18n
4. 构建、验证、同步 `backend/static`

## 十一、默认值与待确认

以下按默认值实施，如无异议即按此开发：

- 工单号前缀 `BK`；优先级默认"中"；所属模块为自由输入
- 附件上限 10MB；允许多个附件
- 提交人**不能删除**工单，只能撤回（待处理/已指派状态）
- IT 管理员可强制关闭任意工单
- 角色配置页面勾选的是 ERP 岗位，人员自动从岗位关系带出
- 一期不做邮件/飞书通知，只做站内消息
